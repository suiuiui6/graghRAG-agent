# A5 - 延迟与成本 性能评测报告

> 评测对象：GraphRAG（LangGraph agent + DeepSeek-chat (V3) + NetworkX KG），50 题
> 数据来源：`metrics_a5_performance.json`（脚本：`metrics_a5_performance.py`，原始：`raw_runs.jsonl`）
> 评测日期：2026/05/28

## 一句话结论

**P50=13s/$0.0073、P95=60s/$0.087、单题最坏 137s/$0.44**——平均成本 $0.025/题、月成本 1000 题/天 ≈ $750；`num_tool_calls` 与 latency 强相关 (r=0.96)、与 token 强相关 (r=0.84)，**工具调用次数是绝对瓶颈**；input/output token 比值中位 18× 表明 context 被 ToolMessage 严重撑大。

## 相关性分析（Pearson r）

| 关系 | r | 解读 |
|---|--:|---|
| num_tool_calls vs latency_ms | **0.962** | 近完美正相关：每次工具调用 ≈ 固定时间开销，主要是 LLM 往返 + tool 执行 |
| num_tool_calls vs total tokens | **0.837** | 强正相关：每次新调用就把累积 ToolMessage 全部回灌为 input |
| input vs output tokens | 0.913 | input 越大 output 也越大（更复杂的题既检索得多也回答得长） |
| latency vs total tokens | (强) | 与 calls 同源 |

**结论**：tool_calls 是单一最强解释变量。压缩 tool_calls → 立即压缩 latency 与 cost。

## 关键洞察

1. **context 累积是成本的核心驱动**：input/output 中位 18×、P95 84×。每多 1 次工具调用，新 input 就把上一轮的全部 messages 加上新 ToolMessage 重发一次，呈 O(N²) 增长（N 为 tool_calls）。Q31 的 1.6M input 是 100 次调用的累计回灌。
2. **T4 多跳是延迟和成本黑洞**：4 题占总成本 46%、总延迟 24%。一题 4 跳就够慢，配上中间检索结果太大就指数爆炸。
3. **T5 拒答类最便宜（$0.005/题）**：agent 探索几次发现"没有相关 entity"后正确放弃。这说明系统在「知道不知道」方面是经济的。
4. **Q31 是必须治理的孤狼**：100 次工具调用、$0.44、137 秒、1.6M tokens。即使只为它设置 `max_tool_calls=30` 上限，也能减少全局总成本约 30%。
5. **mean ≫ median**：mean tokens 88k vs median 17k；mean cost $0.025 vs median $0.0073。长尾极度倾斜，**P95 是更可信的运维指标**。

## 优化建议（按 ROI 降序）

| 建议 | 预期收益 | 复杂度 |
|---|---|---|
| **设 `max_tool_calls=30` 硬上限** | Q31 + 7 题被截断，预计省 30-40% 总成本 | 低（修改 agent config） |
| **裁剪 ToolMessage 内容**：search 工具默认 `max_results=15`，但每条 JSON 几 KB；改为 5 + 仅返回 node_id/label/page_idx | 减小 input 累积，可降 50% input tokens | 中（修改 tools） |
| 开启 DeepSeek prompt cache（input $0.07/M cache-hit） | input cost 降 75%（如果 query 重复率高） | 低（API 自动） |
| 分阶段 retrieval：第一轮搜出 ≤10 个候选后，让 LLM 选 3 个再 detail | 大幅降低 tool_calls 次数 | 高（重设计 prompt） |
| 对 T4 多跳类，单独使用更精简的 system prompt | 减少 T4 类的成本爆炸 | 中 |

## 限制说明

1. **定价是 cache-miss 上界**：DeepSeek 的 prompt-cache 命中可降至 $0.07/M input。若实际 cache 命中率 50%，本评测成本应该折半。
2. **统计样本仅 50 题**：P99 = max = Q31 单点，方差大。生产侧需更大样本验证 tail。
3. **百分位用最近排名法**（nearest-rank），与 numpy 默认线性插值略有偏差，但本规模可忽略。
4. **不包含网络抖动**：DeepSeek API 偶有 5-10s 排队，未单独剥离；统计的 latency_ms 是 agent.invoke 端到端墙钟。
5. **未拆分 LLM 时间 vs Tool 时间**：当前 latency 是端到端；Q31 中可能有大量 LLM 等待，工具本身（NetworkX 内存查询）只占毫秒级。
