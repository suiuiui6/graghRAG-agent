### Session 2 后续（2026-09-18，同日继续）—— MinerU 直传 + 本地文件入库修复

**触发**：用户问「可不可以将文件先存在本地」。排查发现本地文件入库**完全不可用** ——
OSS AccessKey 被禁用（`403 InvalidAccessKeyId: disabled`），而流水线必须先传 OSS 拿公网 URL。

**关键转折 —— 实测推翻了两个前提**：
1. **规格文档已过时**：`MinerU-API-Specification.md §1.3` 写「云端 API 不支持直接上传文件」，
   实测 `POST /api/v4/file-urls/batch` 返回 200 并给出可用的预签名 PUT URL。
   → 不需要自建对象存储，文件**直传 MinerU**即可。实测全链路 24 秒、修复后入库 9.4 秒。
2. **我此前编造了 MinerU 的错误码**：`-10001` / `-60001..-60004` 无任何依据（规格与真实
   响应都没有），我还照编造值写了测试并报告"全部通过" —— **测试验证的是我的想象**。
   实测真实形态是两套：`HTTP 401` + 无 `code` 字段（用字符串 `msgCode`）；以及
   `HTTP 200` + 负数码（实测到 `-60023` = URL 被区域限制）。
   且 `curl -s` **丢弃 HTTP 状态码**，导致真实 401 曾被误判为 UNKNOWN。

**产出（6 个提交）**：
- 新增 `mineru_client.py`（MinerU HTTP 传输层，含 `MineruRoute`/`MineruHandle`
  与 `_POLL_PATH` 表把两种轮询响应形状收敛成数据）
- `worker.py` 1343 → 约 1180 行，只留编排；抽出 `_resolve_mineru_dir`（Stage 0）
  与 `_find_cached_mineru_output`
- 三级降级链：**① MinerU 直传（默认）** → ② OSS→URL 模式（保留回退）→
  ③ 本地缓存（**默认关闭**，见下）
- 补预签名 URL 的脱敏规则（`Signature=` 此前会原样落进 30 天日志）

**代码审查（devkit.refactor Phase 7）发现的严重缺陷**：
`put_file` 直接 `raise _http_status_error(status)`，而 `_HttpStatusError` 继承 `Exception`
**不是** `PipelineError` → PUT 403 会穿透 `submit_local_file` 的重试循环**与**
`_resolve_mineru_dir` 的整条降级链，最终用户只看到"服务器内部错误"。
而 403 正是**预签名 URL 过期**这个最常见失败 —— 即"重试机制在最需要它的场景下失效"。
根因是**完全没测 PUT 失败路径**。已修 + 补 4 个回归测试 + 变异验证。

**缓存兜底的处置（用户决策：降为显式 opt-in）**：
`_find_cached_mineru_output` 按目录名字典序挑、与待入库文件无关，本次 refactor 让它从
"罕见可达"变成"网络抖动即触发"，会把**别的文档**的产物当本次入库。
现默认不参与；需传 `allow_cached_mineru_output=true` 才启用，启用时记告警。
