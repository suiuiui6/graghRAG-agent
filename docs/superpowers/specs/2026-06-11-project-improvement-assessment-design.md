# graghRAG-agent 用户视角改进评估设计

> **版本**: v1.0 | **日期**: 2026-06-11 | **状态**: 待评审
>
> **主题**: 从高频重度使用者视角，评估 graghRAG-agent 当前源码与蓝图之间的产品闭环，识别最值得补强的功能与体验优化点。

---

## 1. 评估目标

本次评估不以“代码好不好看”为核心，而以“高频用户是否愿意持续使用、能否顺畅完成关键任务”为核心。

输出目标有两类：

1. **角色分视角诊断**
   - 终端业务用户：上传文档、问答、看图谱的人
   - 管理员 / 运营者：管理租户、API Key、审计、Webhook、质量面板的人
   - 二次开发者 / 集成人员：接后端 API、嵌入前端、对接 Engine-Vue 的人

2. **路线图建议**
   - 短期：1-2 周内最值得做、能显著提升感知价值的项
   - 中期：形成稳定产品闭环的项
   - 长期：形成差异化与平台化能力的项

---

## 2. 评估范围

本次评估按用户确认，采用 **“已实现代码 + 蓝图差距一起看”** 的口径。

### 2.1 纳入范围

- 前端当前已实现页面与导航闭环
- 后端已暴露 API 与核心服务能力
- 集成链路：文档上传 → 解析 → 建图 → 问答 → 图谱查看
- 管理能力：认证、API Key、租户、审计、质量、Webhook、健康状态
- 文档 / 蓝图中已承诺但尚未形成稳定用户闭环的能力

### 2.2 不纳入范围

- 纯算法效果 benchmark 的定量打分
- 单点代码风格优劣
- 与业务目标无关的泛化重构建议

## 4. 分析框架

采用 **“角色视角 × 蓝图差距 × 迭代阶段”** 三维框架。

### 4.1 角色视角

每类角色都从以下问题切入：

1. 我第一次进入系统，能否快速理解它能做什么？
2. 我最高频的任务，是否有稳定、顺滑、低心智负担的路径？
3. 当结果不理想时，我能否知道哪里出了问题、下一步该怎么做？
4. 当我开始高频使用时，是否出现明显重复劳动或“半成品感”？

### 4.2 蓝图差距

每个发现会标注为以下两类之一：

- **已实现但感知弱**：代码已有能力，但入口、反馈、可解释性或串联体验不足
- **蓝图承诺未闭环**：文档已设计，但用户路径、接口、界面或运维动作尚未形成可用闭环

### 4.3 迭代阶段

每个建议会落到：

- **短期**：补入口、补反馈、补默认路径、补文档、补可观测性
- **中期**：补跨页面闭环、补数据模型一致性、补真正可复用的工作流
- **长期**：补多文档协同、企业治理、生态集成、智能体能力差异化

---

## 5. 输出结构

正式评估结论按以下结构输出：

### 5.1 整体判断

回答：这个项目当前更像什么阶段的产品，最主要的价值已经在哪里，主要瓶颈又卡在哪里。

### 5.2 三类用户分视角诊断

每类角色下统一输出：

- **已具备的亮点**
- **高频使用时的主要断点**
- **最该优先补的功能 / 优化项**

### 5.3 蓝图差距判断

统一归纳：

- 哪些能力已经存在，但用户感知不到
- 哪些能力文档写得很全，但真实闭环还不成立

### 5.4 路线图建议

- **短期（1-2 周）**：最高回报项
- **中期（1-2 个迭代）**：产品闭环项
- **长期（平台化）**：差异化项

---

## 6. 评估标准

建议项的优先级将按以下标准排序：

1. **高频度**：是否影响最常见任务
2. **闭环价值**：是否让一个用户流程真正走通
3. **感知强度**：用户是否能明显感觉更好用
4. **实现杠杆**：是否能复用现有代码与已有 Phase 能力
5. **战略一致性**：是否与企业演进蓝图、Engine-Vue 集成方向一致

---

## 7. 风险与限制

- 蓝图文档覆盖范围大于当前用户可见闭环，评估时必须避免把“有设计”误判成“已可用”。
- 若实际源码与 `CLAUDE.md`/架构文档不一致，以真实代码行为为准。
- 本次输出优先给产品改进判断，不代替后续详细实施方案。
